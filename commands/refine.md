現在のセッションで変更・新規作成したファイルを対象に、以下を順番に実行してください。

## ステップ1: 品質・保守性の改善（修正適用）

Agent ツールで `code-simplifier` を起動し、機能を完全に保持したまま構造・可読性・規約準拠の観点で改善してください。

加えて、**効率性（無駄な計算・メモリ使用・I/O）の観点**も伝えてください: パフォーマンスを犠牲にしている明らかな箇所があれば指摘・修正してください。ただし可読性とのトレードオフは可読性を優先します。

フォーカス指示（任意、ユーザー引数）: $ARGUMENTS

## ステップ2: 正確性バグの検出（報告のみ）

ステップ1の修正が完了したら、`/code-review` を実行して正確性バグを検出してください。ここでは修正は行わず報告のみとし、検出されたバグへの対応はユーザー判断に委ねてください。

## ステップ3: セキュリティレビュー（条件付き・報告のみ）

ステップ1の変更が**セキュリティ関連面**——入力処理 / 認証・認可 / 外部通信（HTTP・SSRF 面）/ 機密データ・シークレット / ファイル・コマンド実行 / SQL・クエリ生成——のいずれかに触れる場合のみ、Agent ツールで `security-reviewer` を起動し、報告のみのレビューを行ってください（修正は適用せず、対応はユーザー判断に委ねる）。

いずれにも触れない変更（ドキュメント・設定・純粋なリファクタ等）はスキップし、完了報告に「セキュリティ関連の変更なし → スキップ」と明記してください。

リポジトリ全体の深い監査（脅威モデリング・データフロー追跡・パッチ生成）が要る場合は、`/claude-security`（マルチエージェント深層スキャン）の実行をユーザーに促してください。

## 完了報告

両ステップ完了後、以下を**専門用語を避けた平易な日本語**で報告してください。
コードに不慣れな読み手を想定し、業務・運用レベルの言葉で説明します。

### ステップ1（適用済み修正）

各変更を以下の形式で:
- **変えた箇所**: ファイル名と関数名
- **何を変えたか**: 1〜2行
- **効果**: 読みやすさ向上 / バグの予防 / 速度向上 等を一言で

無ければ「変更なし」。

### ステップ2（検出されたバグ）

検出件数と重大度別の内訳を冒頭に。各バグは以下の3点セットで:

1. **何がまずいか**: コードの現象を1行
2. **放置した場合の実害**: ユーザー / データ / 業務にどう影響するかを具体的に
   （例: 「特定の入力で計算結果がずれて報告書の数値が間違う」
        「夜間バッチが止まって翌朝データが揃わない」
        「データが上書きされて元に戻せない」
        「同時アクセスで稀にエラー画面になる」）
3. **推奨アクション**: 緊急 / 通常 / 様子見、のいずれかと理由

専門用語（race condition、null safety、memoization、N+1 等）を使う場合は
**必ず日常語の補足**を添える:
  - race condition → 「2つの処理が同時に走るとデータがおかしくなる現象」
  - N+1 問題 → 「1件取るたびに DB アクセスが発生し件数比例で遅くなる現象」

問題なしの場合は「問題なし」のみで構いません。

### ステップ3（セキュリティレビュー）

セキュリティ関連の変更が無ければ「セキュリティ関連の変更なし → スキップ」と一行で。
実施した場合は検出件数と、各指摘を「何が危険か（1行）／悪用された場合の実害／推奨アクション（緊急・通常・様子見）」の3点セットで。専門用語には日常語の補足を添える（例: SSRF → 「サーバを騙して内部リソースへ不正アクセスさせる攻撃」）。
